# 多人场景下单目标实时选择方案

## 目的

这份文档用于评估这样一个方向的可行性：

- 场景里可以同时出现多人
- 系统只实时重建和可视化其中一个目标人
- 后面的 3D、augmentation、IK 仍然尽量复用现有单人 realtime 管线

这份方案的直接动机，是我们在 `demo_tiaosan_4cam` 上观察到：

- 不同相机会选到不同的人
- 整体运动方向有时看起来还算合理
- 但局部动作、姿态和 IK 结果会明显错误

也就是说，当前问题的核心并不只是 3D 或 IK 不稳，而是 **2D 目标人身份在多视角之间不一致**。

---

## 当前问题

当前 realtime 主链大致是：

```text
frame source
-> pose2d
-> pose2d quality mask
-> triangulation
-> offline-like quality
-> filter
-> augmentation
-> IK
-> visualizer
```

其中 2D 这层现在的行为是：

1. 每个相机各自做多人检测
2. 每个相机各自用 `sort_people_sports2d()` 做跨时间排序
3. 每个相机最后只保留 `keypoints[0]`

这意味着当前系统默认假设：

- 每个相机自己的 `#0`
- 恰好都是同一个物理人

但这个假设在多人场景里很容易失效。

例如：

- `cam01` 选到了目标人
- `cam03` 选到了旁边的人
- `cam05` 又选回目标人
- `cam07` 选到了另一个人

而这些 2D 结果后面会被当成“同一个人”的多视角输入送进 triangulation。

---

## 我们已经确认的事实

我们已经做过一个调试脚本，用来可视化每个相机当前到底选中了谁：

- `Pose2Sim/realtime/debug_selected_person.py`

它会导出若干帧的 4 宫格图，显示：

- 每个相机中所有候选人
- 当前 realtime 实际保留的人

从这些调试结果已经确认：

- 有些相机选中了目标人
- 有些相机选中了旁边的人
- 有些相机当前真正的 `#0` 轨迹甚至已经失联

这说明当前 `demo_tiaosan_4cam` 效果差，主因很可能是：

**目标人选择错误或不一致**

而不是仅仅因为：

- augmentation 参数不好
- IK 参数不好
- 或坐标系问题

---

## 核心方向

不建议一上来就做完整的多人实时重建。

更合理的目标是：

**多人场景 -> 先选一个目标人 -> 继续走现有单人 realtime 管线**

也就是：

```text
多人2D候选
-> 单目标选择
-> 单人的多视角2D
-> 现有 3D / augmentation / IK
```

这样做的好处是：

- 后半段主线可以尽量不动
- 只需要补前半段的“选谁”逻辑
- 更符合实际应用场景

---

## 可行性分析

## 结论

**可行，难度中等，而且值得做。**

它明显比“完整多人 realtime IK”更现实，也更适合当前项目阶段。

---

## 为什么可行

### 1. 后半段主线基本可以复用

如果目标只是“多人场景下只追一个目标人”，那么下面这些模块理论上都可以保留：

- triangulation
- offline-like quality
- filtering
- augmentation
- IK
- visualizer

真正需要补的是：

- 2D 层保留多人候选
- 在多候选里选出目标人
- 再把目标人的 2D 结果送入现有单人链

### 2. 当前代码结构本身就适合插这层

当前代码中，2D、跨相机打包、后续 3D/IK 是分开的。

涉及的关键文件有：

- `realtime/pose2d.py`
- `realtime/pipeline.py`
- `realtime/packets.py`

这意味着我们可以在：

- `pose2d`
- `associate`
- `triangulation`

之间插入一个专门的目标选择层，而不必重构整条系统。

### 3. 问题规模比“多人同时重建”小很多

我们并不需要：

- 为每个人维护一套 IK
- 为每个人维护一套 buffer
- 为每个人都做可视化

只需要做到：

- 多人场景里，稳定地选出一个目标人
- 并且持续跟踪这个目标

这会把问题难度降很多。

---

## 为什么又不是一个特别轻的改动

### 1. 当前 packet 是按单人设计的

现在的：

- `Pose2DPacket`
- `MultiViewPosePacket`

都是单人的语义。

如果要支持“多人候选 -> 选一个目标人”，前半段数据结构要么需要：

- 新 packet 类型

要么需要：

- 在 metadata 里临时挂上多候选信息

### 2. 当前 tracking 是每个相机独立做的

现在的 `keypoints[0]` 表示的是：

- 这个相机里当前排序后的第 0 号轨迹

而不是：

- 整个系统里我们想跟踪的那个目标人

所以如果不加新逻辑，跨相机仍然可能选不同的人。

### 3. 多人复杂场景本来就更容易漂

像幼儿园、课堂、多人康复场景，常见问题包括：

- 遮挡
- 体型小
- 动作快
- 穿着相似
- 目标离开又回来

这意味着即便一开始选对了目标，后面也仍然要考虑：

- 丢失目标怎么办
- 重新找回时怎么避免跳到别人身上

---

## 最推荐的第一版方案

## 推荐做法

先做：

**anchor camera 初始化选人 + 后续持续追踪**

也就是：

1. 固定一个主相机，例如 `cam01`
2. 在主相机第一帧或前几帧里，把所有候选人框出来并编号
3. 用户选择目标人一次
4. 后面系统围绕这个目标人持续追踪

---

## 为什么这个版本最合理

### 1. 它直接解决第一帧选错的问题

当前最大的歧义就是：

- 第一帧的 `#0` 是系统自己按分数/排序决定的
- 不保证是我们真正想跟踪的人

只要一开始明确指定目标人，这个歧义就消失了。

### 2. 它不需要完整多人自动关联

我们不用一开始就追求：

- 系统自己理解“哪一个才是主角”

而是允许一次轻交互，让用户告诉系统：

- “就是这个人”

这在实际应用里是合理的。

### 3. 对康复和幼儿园场景都成立

无论是：

- 幼儿园里跟踪某个孩子
- 康复场景里跟踪某个患者

都天然存在一个“目标人”。

因此初始化选人并不是多余交互，而是明确任务语义。

---

## 初始化怎么做最合适

第一版最推荐的是：

### 编号选择

流程：

1. 在 anchor camera 的启动帧中，检测出所有候选人
2. 给每个人画框并编号
3. 用户输入一个编号
4. 这个编号对应的人就成为目标人

为什么先推荐这个，而不是鼠标点选：

- 最简单
- 最容易实现
- 最适合先验证方向

后面如果方向证明有效，再升级成：

- 鼠标点击选人
- 或更自然的图形交互

---

## 推荐的系统结构

建议在现有 realtime 主线前半段加一层：

```text
frame source
-> pose2d candidates
-> target selector
-> selected single-person multiview packet
-> existing 3D / augmentation / IK pipeline
```

其中：

- `pose2d candidates`：每个相机保留多个候选人，而不是立刻丢到只剩一个
- `target selector`：负责初始化目标人、持续追踪目标人、必要时处理丢失
- downstream pipeline：仍然沿用当前单人流程

---

## 建议的实现分阶段计划

## Phase 1：保留多人候选

目标：

- 不再在 `pose2d.py` 里立刻只取 `keypoints[0]`
- 先保留 top-N 候选人

建议：

- 每个相机先保留 top-3 或 top-5

这一步的意义是：

- 给后续目标选择提供候选集

涉及文件可能包括：

- `realtime/pose2d.py`
- `realtime/packets.py`

---

## Phase 2：加入 target selector

目标：

- 在后续 3D 之前，显式决定“这一帧选哪个人”

建议新增一个模块，例如：

- `realtime/target_selector.py`

它的职责包括：

- 维护初始化状态
- 维护目标人状态
- 根据候选人选出当前目标
- 输出仍然是单人的多视角 2D 数据

---

## Phase 3：初始化选人

目标：

- 在 anchor camera 中确定目标人是谁

建议第一版：

- 编号选择

流程：

1. 启动时在 anchor camera 上输出一张编号图
2. 用户输入目标编号
3. 系统记录这个人的：
   - bbox 中心
   - skeleton 中心
   - 关键点布局

这一步只需要发生一次。

---

## Phase 4：持续追踪

目标：

- 后续帧尽量继续跟踪同一个目标

建议第一版策略：

- 以上一帧目标人的中心位置为锚
- 在当前帧候选人里，选离它最近的那一个

可以先使用：

- bbox center
- 或 torso center

这一步的本质是：

- 把“当前随便追一个 `#0`”
- 改成“继续追我们已经指定好的那个目标人”

---

## Phase 5：其他相机的目标选择

目标：

- 不只是 anchor camera 选对
- 其他相机也尽量选到同一个目标人

第一版建议先简单一些：

- 在每个相机里，也用和目标人相似的空间位置、骨架中心、稳定性来选

更进一步的版本再考虑：

- 做一个轻量的跨视角一致性检查

但建议不要第一版就搬完整离线多人关联。

---

## Phase 6：丢失与重获

目标：

- 目标短时丢失时，系统不要立刻跳到别人身上

建议增加：

- lost 状态
- 最大允许跳变距离
- 短时空窗保留
- 条件满足时再重新捕获

这个阶段很重要，因为多人场景里：

- 跳错人往往比短时掉点更糟

---

## 最小可行版本（MVP）

如果只做一个最小版本，建议是：

1. 每个相机保留 top-3 候选
2. 只做 anchor camera 初始化选人
3. 用编号方式指定目标人
4. anchor camera 后续按中心距离继续追踪
5. downstream 仍然完全沿用现有单人管线

这个版本的价值在于它能快速回答一个核心问题：

**只要一开始把目标人选对，后面的 3D 和 IK 会不会明显变好？**

如果答案是会，那这条路就值得继续做下去。

---

## 更实用的第一版

MVP 之后，更推荐的第一个真正可用版本是：

1. 每个相机保留 top-3 候选
2. anchor camera 初始化目标人
3. anchor camera 继续稳定追踪
4. 其他相机也做简单目标匹配
5. 后面的 3D / quality / augmentation / IK 不变

这个版本最适合：

- 幼儿园场景
- 多人康复场景

---

## 风险分析

### 风险 1：初始化之后目标还是会漂

缓解方式：

- 限制每帧允许跳动的距离
- 丢失时不要立刻换人
- 增加短时 lost 状态

### 风险 2：交互太重

缓解方式：

- 只在启动时交互一次
- 第一版先做编号输入
- 后面再升级成更自然的点击方式

### 风险 3：其他相机仍然会选错

缓解方式：

- anchor camera 驱动目标身份
- 后面逐步增加跨视角一致性约束

### 风险 4：多人场景仍然过于复杂

缓解方式：

- 把目标限定为“已知目标人”
- 场景尽量固定
- 优先追求“稳定单目标”，而不是“完全自动多人”

---

## 研究价值

这个方向不只是工程 patch，也可以形成一个比较明确的研究问题：

**多人复杂场景中的单目标实时 markerless 运动学重建**

它的价值在于：

- 真实场景往往不是干净的单人环境
- 但又没有必要一上来做完整多人 biomechanics
- 在“单人 clean scene”和“完整多人 realtime”之间，存在一个很实用的中间层

这个中间层就是：

**多人场景下的单目标初始化与持续追踪**

---

## 最终建议

建议推进这个方向。

### 原因

因为当前证据已经很明确：

- `demo_tiaosan_4cam` 的主要问题是选人不一致
- 不先解决目标身份问题，后面继续调 IK 和 augmentation 没有太大意义
- 一次初始化交互非常现实，而且很适合你的应用场景

### 推荐策略

- 保留当前四机位稳定主线作为 baseline
- 在新的研究分支里实现“多人场景单目标选择”
- 第一版先做 anchor camera 初始化选人
- 不要一开始就做完整多人 realtime

---

## 建议的下一个具体动作

先做最小实验版本：

1. `pose2d.py` 保留 top-3 候选
2. 新增一个 `target_selector`
3. 用 anchor camera 第一帧编号选择目标人
4. 后面的 3D / augmentation / IK 保持不变
5. 与当前 `keypoints[0]` 方案做直接对比

这个实验会很快告诉我们：

**只要目标人选对了，当前这条 realtime 主线到底能不能在多人场景里明显改善。**
