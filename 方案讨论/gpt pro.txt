================================================================
                    在线可视化实施路线总结
================================================================

【核心结论】

这个项目可以做成在线可视化，但不是"改几行代码"级别，
而是要新增一条实时链路。

第一阶段最稳的目标，不是"强行在 OpenSim GUI 里实时播放"，而是：
    实时前半段数据流 + 小窗口 IK + OpenSim API Visualizer 实时显示。

OpenSim 官方对运行时可视化的推荐路径是：
    Model.setUseVisualizer() / getVisualizer() 这类 API

注意：VisualizerUtilities.showMotion() 会阻塞直到窗口退出，
不适合做流式在线显示。官方文档明确指出，脚本环境里不能直接访问
OpenSim 自带 plotter/visualizer，应使用 Simbody visualizer。

================================================================
【仓库现状判断】
================================================================

当前状态：
  - perform_scaling()：整段读入 TRC → 剔除异常帧 → 统计 segment ratio
    → 调用 ScaleTool，典型的离线文件流水线
  - perform_IK()：回写 IK XML → 整段时间范围执行
    InverseKinematicsTool(...).run()
  - markerAugmentation.py：把整段 TRC 送进 LSTM/ONNX，
    不是现成的在线模块

配置关键信号：
  1. use_simple_model = true 时，IK 会快 10 倍以上
  2. Kalman 配置：smooth = true（注释说明：除非需要实时滤波，否则应为 true）
  3. OneEuro 配置注释写着更适合实时，但当前实现为双向零相位，
     不能直接用于在线滤波

================================================================
【两阶段目标拆分】
================================================================

阶段 A：先做"本地实时显示 OpenSim 结果"
  → 在 Python/OpenSim 进程里，实时更新模型姿态
  → 作用：验证求解链路正确性

阶段 B：再做"网页/浏览器在线可视化"
  → 把关节角、marker、状态流推给 Web 前端
  → 作用：产品化界面

================================================================
【可操作详细步骤】
================================================================

步骤 1：阶段 0 — 环境与基准验证（必须先做，不可跳过）

  必须验证的 6 件事：
    ① import opensim 是否成功
    ② Model.setUseVisualizer(True) 是否能开出窗口
    ③ model.getVisualizer().show(state) 是否能持续刷新
    ④ TimeSeriesTableVec3 能否程序化构造
    ⑤ MarkersReference 能否由 TimeSeriesTableVec3 构造
    ⑥ InverseKinematicsSolver + assemble() + track() 是否跑得稳

  阶段 0 验收标准：
    - 能稳定显示最新状态
    - 能在 5–10 帧小窗口上做一次 IK
    - 能从最后一个 state 正常提取关节角
    - 显示线程不会卡死上游处理链路

  ⚠️ 注意：任何"2–15ms""200–450ms"之类的数字只能作为工程假设，
     必须在实际机器上实测确认。

----------------------------------------------------------------

步骤 2：新增 Pose2Sim/realtime/，不改坏离线版

  目录结构：
    Pose2Sim/realtime/
      ├── __init__.py
      ├── capture.py          # 多相机实时采集
      ├── packets.py
      ├── pipeline.py         # 串起整条实时链路
      ├── triangulate_frame.py  # 单帧三角化
      ├── filter_realtime.py  # 单向 Kalman / 单向 OneEuro
      ├── marker_buffer.py    # 滑动窗口缓存
      ├── opensim_ik.py       # 小窗口 IK
      └── opensim_viz.py      # API Visualizer 封装

  现有 kinematics.py 只抽公共函数（加载 scaled model、准备
  visualizer、提取 joint angles、构造 marker weights）；
  离线的 perform_scaling() 和 perform_IK() 保留不动。

----------------------------------------------------------------

步骤 3：前半段改成"内存总线"

  当前（文件总线）：
    poseEstimation → JSON → personAssociation → JSON
    → triangulation → TRC → kinematics → XML/MOT

  在线版（内存总线）：
    camera frames → 2D keypoints → matched persons
    → 3D markers → filtered markers → IK state

  中间结果全部在内存里传 numpy / dict / packet 对象，
  不再逐帧落盘。

----------------------------------------------------------------

步骤 4：相机同步和标定

  - 标定：继续沿用离线流程（一次性工作）
  - 同步：上线前先测出固定偏移量，在线阶段直接套用，
    不在实时阶段做整段互相关自动同步
  - 如条件允许，优先使用硬件同步

----------------------------------------------------------------

步骤 5：前半段逐帧化 — 打通"采集 → 2D → 关联 → 3D"

  实时主循环：
    ① 多路 cv2.VideoCapture(camera_id) 取帧
    ② 每路跑 RTMPose / rtmlib
    ③ 做单帧 person association
    ④ 做单帧 triangulation
    ⑤ 对 3D markers 做实时滤波
    ⑥ 塞进 marker buffer

  注意：
  - person association 核心几何逻辑本来就是按帧算 affinity，可逐帧调用
  - triangulation 核心也是逐帧的；不适合实时的是后处理（整段插值、
    片段裁剪、TRC 写盘）
  - 在线版需抽一个 triangulate_frame(...)，不继续依赖整段 Q_tot 后处理

----------------------------------------------------------------

步骤 6：滤波 — 先选 Kalman 单向版，OneEuro 后补

  可直接用于在线：
    ✅ Kalman(smooth=False)

  不能直接用于在线：
    ❌ Butterworth / Butterworth on speed（双向/整段）
    ❌ GCV spline / LOESS（整段）
    ❌ 当前 OneEuro（双向零相位实现）

  第一版直接用 Kalman 单向版，等系统跑起来后再补单向 OneEuro。

----------------------------------------------------------------

步骤 7：缩放 — 首选预缩放，不做"随时在线自动缩放"

  首选方案 — 预缩放模型：
    ① 先离线跑一次 perform_scaling()
    ② 得到个人化 .osim 文件
    ③ 在线阶段直接加载这个模型

  备选方案 — warm-up 缩放：
    ① 被试先站立 3–5 秒
    ② 用这段数据做一次缩放
    ③ 之后锁定模型进入在线模式

  ⚠️ 不要在第一版做"运行过程中持续自动缩放"。

----------------------------------------------------------------

步骤 8：在线 IK — 改用小窗口 Solver，不走 Tool

  流程：
    ① 维护一个 5–15 帧的 SlidingMarkerBuffer
    ② 每次取最新窗口
    ③ 构造 TimeSeriesTableVec3
    ④ 构造 MarkersReference
    ⑤ 构造 InverseKinematicsSolver
    ⑥ 以上一窗口末状态作为初值
    ⑦ 首帧 assemble()
    ⑧ 后续帧 track()
    ⑨ 取最后一帧 state 用于显示和输出

  窗口大小建议：
  - 不要一开始就设成 1 秒（30fps 下即 30 帧，会有明显缓冲延迟）
  - 首版建议 5–10 帧，兼顾时序稳定性与交互延迟

----------------------------------------------------------------

步骤 9：可视化分两阶段

  第一阶段 — API Visualizer（本地）：

    model.setUseVisualizer(True)
    state = model.initSystem()

    每次解出最新状态后执行：
      model.realizePosition(state)
      model.getVisualizer().show(state)

    ⚠️ 不要用 VisualizerUtilities.showMotion()（会阻塞）

  第二阶段 — 网页浏览器可视化：

    后端：
      - FastAPI / Flask
      - WebSocket 推送
      - 每次推送：timestamp / joint_angles / markers_3d / quality

    前端：
      - Three.js / Babylon.js 显示骨架或人体模型
      - Plotly / ECharts 画 joint angle 曲线

    原则：OpenSim 负责求解，浏览器只负责显示，
    不要让浏览器直接"驱动 OpenSim"。

----------------------------------------------------------------

步骤 10：多线程架构

  至少拆成 3 条线程：

    线程 A：采集 + 2D 姿态
    线程 B：关联 + 三角化 + 滤波
    线程 C：小窗口 IK + 可视化 + 输出

  核心原则：显示层只显示"最新可用状态"，不能反向卡住上游求解。

【实现难度评估】
================================================================

目标 1：本地实时显示 OpenSim 结果
  难度：7.5 / 10（中高难度，可落地）

  主要难点：
    - OpenSim Python API 在线 IK 的实际行为
    - 把文件总线改成内存总线
    - 多线程下的稳定性与延迟控制

目标 2：浏览器网页在线可视化
  难度：6 / 10（本地链路打通后）
  难点主要是工程集成，核心算法已解决。

最不确定的地方：
  不是 pose estimation，不是三角化，也不是前端，而是——
  InverseKinematicsSolver + MarkersReference + 小窗口 track()
  在实际机器上的稳定性和速度。

  ➡ 这就是为什么"阶段 0 必须先做"。

【必须修正的说法】
================================================================

❌ "单帧 IK 2–15ms / 总窗口 200–450ms"
   → 只能作经验判断，不能作承诺，必须以实机测试为准

❌ "当前 OneEuro 可以直接用于实时"
   → 错误。当前仓库实现是双向零相位版本，不能直接用于在线

❌ "第一阶段可以把 OpenSim GUI 做成实时后端"
   → 不建议，官方支持路径是 API/Simbody visualizer

❌ "伪代码按文中写法就能直接跑"
   → OpenSim Python 绑定是 SWIG 包装，版本差异和构造细节
     都需要在实际机器上适配

❌ "第一阶段完全不需要任何 fallback"
   → 如阶段 0 证明 Python API 不满足要求，低优先级 fallback
     是合理的工程态度
